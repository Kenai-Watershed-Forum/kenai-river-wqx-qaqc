**CDX re-upload attempt: project.csv/station.csv succeeded, results_activities.csv blocked by mismatched WQX Web import configuration (root cause found, fix in progress).**

Station required "This file contains existing data only"; a first attempt with "All New Data" failed with a harmless/superseded "Risk of Overwriting Data" warning on all 22 records.
- `results_activities.csv` ("Results & Activities" import) failed 4 times in a row with a generic WQX Web error: "Import Failed" / event log "System Error" + "System Process Halted" (Context: "Row 2"). The UI exposes no further diagnostic detail.
- Found and fixed three real bugs in `generate_cdx_export.R` (both `functions/appendix_a_scripts/` and `other/qaqc_repo_transition/functions/` copies) while troubleshooting, none of which turned out to be the actual crash cause:
  1. **Literal "NA" text bug**: `write.csv(..., row.names = FALSE)` without `na = ""` wrote 8,848 literal `NA` tokens into the file instead of blank fields. Fixed by adding `na = ""` to all three `write.csv()` calls in both script copies, and repairing the on-disk file.
  2. **Missing `Monitoring Location Name` column**: `MonitoringLocationName` was referenced inside the `Activity ID` paste formula but never re-assigned to its own output column in the big `mutate()` block, so `.keep = "unused"` silently dropped it, leaving the export one column short of the 55-column `AWQMS_KWF_Baseline_2021.xlsx` template. Fixed by adding an explicit ``Monitoring Location Name`` = MonitoringLocationName` mapping in both script copies; repaired the on-disk file by joining the name in from `station.csv`.
  3. **Unicode hyphen corrupting longitude**: station KENAI_WQX-10000028 (KR RM 43) had `Activity Longitude` written with a Unicode HYPHEN (U+2010) instead of ASCII `-`, across 29 rows -- a previously-known issue (see the Q28 comment in `chapters/appendix_a.qmd` ~line 1341, "Sheesh!") whose existing `iconv()` fix was only ever applied to a throwaway leaflet-map object, never to `export_dat`. Only patched on the output file directly this session; **not yet fixed at the pipeline source**.
- After all three fixes, a systematic scan of all numeric columns confirmed the file was structurally clean (55/55 columns, zero literal NA tokens, zero non-ASCII bytes, dissolved-metal fractions intact) -- yet the import still failed identically a 4th time.
- **Root cause found**: downloaded the live CDX import configuration for Results & Activities (`other/output/wqx_formatted/Import_Configuration_20260928.cfg`, an XML file) and compared it column-by-column against the export. WQX Web maps import columns **by position** (`ColumnNumber`), not by header name (consistent with "Ignore First Row" being checked). The only saved Results & Activities configuration for this organization, `KWF_Results_Baseline_Template` (Uid 8515, description: "intended to mimic the AQWMS format provided by ADEC in Spring 2022"), is an old 44-column template with a completely different column order. Its position 9 expects a numeric `Activity Latitude`; our export puts `Activity End Date` (a date string) there -- guaranteed to crash parsing on the very first data row, exactly matching the observed "Row 2" failure (row 2 of the file = first data row, after the header). Confirmed via screenshot of the full "Import Configurations" list (owner: Ben Everett Meyer) that no alternate/matching configuration exists.
- Considered hand-authoring a replacement `.cfg` XML directly (the format is fully visible/writable), but found that roughly 15-16 of the needed WQX elements do not appear anywhere in the one known-good reference config, so their internal numeric `ElementUid` values are unknown and not derivable from the element name -- not safe to guess.
- **User decision**: `Biological Intent` and `Subject Taxonomic Name` will never apply to this project (no biological/tissue sampling). Removed both from the export pipeline entirely (both `generate_cdx_export.R` copies: removed the two `mutate()` assignments, changed `select(one_of(wqx_colnames))` to `select(any_of(wqx_colnames))`) and from the on-disk `results_activities.csv` (confirmed both fields were 830/830 NA beforehand). This reduces the export to **53 columns** and reduces the unknown-`ElementUid` count from 16 to 14.
- **Note for future sessions**: both `generate_cdx_export.R` copies and `AGENTS.md` use CRLF line endings; the `edit` tool's exact-string matching intermittently failed against CRLF content in this session even when the visible text matched exactly. Direct byte-level replacement via a short Python/bash snippet was used as a fallback each time this happened.
- **Next step (not yet done)**: build a new Results & Activities import configuration in WQX Web ("Add New" -> "from an existing configuration or template" -> start from Uid 8515 to reuse its ~28 known-good element UIDs), fix the column order to the new 53-column sequence, add the 14 elements with unknown UIDs via the UI's name-based dropdown (list in AGENTS.md Next Session Priorities), and add `Activity Start Time Zone`, `Activity End Time Zone`, `Analysis Start Time Zone` as constant-value (`AKDT`) Generated Columns (these three have no file column at all, same pattern as the existing `Organization ID -> KENAI_WQX` generated column). ### Session Entry (2026-10-14) — addendum to 2026-09-29/2026-10-13 entries above

**WQX Web config rebuild complete and working; all data-level validation errors in `results_activities.csv` found and fixed; CDX upload succeeded.**

- **Config-level fix (corrects a wrong theory from 2026-10-13's planning).** The remaining config problem was not column order but a design-time quirk: mapping columns I/J to `Activity End Date`/`Activity End Time` (both always blank in the data) combined with the `Activity End Time Zone` constant Generated Value triggered a blanket "Activity End Time required" error on all 830 rows. Root cause: WQX Web requires a value for a Generated Value's parent element **whenever that element has a column mapping at all**, regardless of whether the mapped column's data is populated. Fix (done live in the UI): changed columns I and J to `{Ignore Column}`; the `Activity End Time Zone` Generated Value requirement disappeared automatically once nothing referenced it. Re-saved with zero validation warnings. Re-running the import against the (still pre-data-fix) 830-row CSV cleared all 830 "Activity End Time required" errors with no new errors introduced, isolating the remaining errors as pure data-content issues.
- **Data-level fixes made in `functions/appendix_a_scripts/format_wqx.R` and `functions/appendix_a_scripts/generate_cdx_export.R`, confirmed via two full `quarto render chapters/appendix_a.qmd` passes against two successive validation logs** (`other/temporary/import_log_20261014_v2.csv`, `..._v3.csv`):
  - Thermal Preservative `"Cold packs"` -> `"Cold Packs (4 deg C)"` (830 rows, `format_wqx.R`)
  - Result Detection Limit Type 1 `"Limit of Quantitation"` -> `"Practical Quantitation Limit"` (830 rows, `format_wqx.R`; confirmed via SGS's own terminology doc that LOQ = renamed PQL)
  - Sample Container Color `"Brown"` -> `"Amber"` for BTEX rows (48 rows; fixed in the `sample_container_type_color` sheet of `other/input/wqx_templates/wqx_template_matching_table.xlsx`, not in code)
  - Characteristic Name translation added in `generate_cdx_export.R` (applied only at final export, so upstream narrative chunks can keep using lab terminology): `"Total Nitrate/Nitrite-N"` -> `"Nitrate + Nitrite"` (48 rows); `"Calcium, Total"`/`"Magnesium, Total"` -> `"Calcium"`/`"Magnesium"` (WQX conveys total vs. dissolved via Result Sample Fraction, not the name); `"P & M -Xylene"` -> `"m,p-Xylene"` (WQX id 3585, distinct from the all-isomer-sum "Total xylenes"/id 8052)
  - Method Speciation required by WQX's synonym matching for two characteristics: `"Total Phosphorus"` (resolves to "Total Phosphorus, mixed forms") -> `"as P"`; `"Nitrate + Nitrite"` -> `"as N"` (both 48 rows; confirmed against live WQX MethodSpeciation domain CSV)
  - Result Qualifier `"ND"` blanked out (1 row; redundant with Result Detection Condition "Not Detected")
  - "Result Measure Value is required when Result Measure Unit is provided" (445 rows): root cause was non-detect rows correctly leaving Result Value blank but still carrying a Result Unit. Fixed by blanking Result Unit whenever `result` is NA.
  - "Result Detection Limit Value is required" (162 rows): root cause was Result Detection Limit Type 2 ("Method Detection Level") always being populated even when `lod` was NA. Fixed to only set Type 2/Unit 2 when `lod` is non-NA.
  - **Unicode-hyphen longitude bug, finally fixed at the pipeline source** (previously flagged in the 2026-09-28 entry as "only patched on the output file directly... not yet fixed at the pipeline source"): traced to the `site_coordinates` sheet of `wqx_template_matching_table.xlsx`, where KR RM 43's longitude cell held a Unicode HYPHEN (U+2010, byte sequence `e2 80 90`) instead of ASCII `-` (29 rows). Corrected the cell directly via `openxlsx`, and added a defensive `stringr::str_replace_all(longitude, "[\u2010-\u2015\u2212]", "-")` sanitizer immediately after the `site_coords` join in `format_wqx.R` so any future stray Unicode dash in lat/long is normalized automatically rather than silently breaking an import again.
