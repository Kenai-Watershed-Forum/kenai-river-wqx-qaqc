Annual QA/QC Pipeline

2.1 Introduction

This document runs one project year’s raw lab files through ingestion, QA/QC evaluation, WQX formatting and CDX export. Everything year-specific is read from config.yml, year_files/ and reference/.

The structure of Part C follows the Data Evaluation Checklist provided by the Alaska Department of Environmental Conservation. Results that fail QA/QC are marked Rejected before upload to the EPA Water Quality Exchange (WQX); they remain in the public record.

Question tags in Part C (AUTO, MANUAL, MIXED) are provisional and show how much of each answer the pipeline can compute. Chunks marked eval: false are not yet ported from project_year/2025.qmd.

17.) Were preservation, hold time and temperature requirements met?

Hold time is the elapsed time from collection to the start of analysis, compared with reference/wqx_templates/sample_holding_times.csv. In-situ meter readings are Not applicable. 18.) Are dissolved metal quantities less than total metals quantities?

For every characteristic measured in both fractions at the same location and date (primary samples only), the dissolved result is compared with the total result. A Dissolved result comes from a filtered sample and a total result from an unfiltered one (SGS flags these L and . in its data deliverable; Total and Unfiltered are both treated as total). Results are compared in ug/L. A pair is Not comparable when either result is a non-detect or below the quantification limit. Dissolved above total is reported in two tiers: within tolerance, when the relative percent difference is no larger than the duplicate RPD limit for that characteristic (rpd_threshold()), or exceeding tolerance. The tolerance is a project convention; the QAPP does not state one.

This comparison does not reject anything by itself. Every pair that exceeds tolerance needs a decision recorded in year_files/{year}_data_flag_decisions.csv (flag Y rejects, N accepts, with notes; a blank result_sample_fraction applies to both results). The pipeline stops before the export until each exceedance has a decision.

19.) Are the duplicate sample(s) RPD (Relative Percent Difference) within range described in QAPP?

Each original and field duplicate pair is evaluated under two rules side by side (assess_rpd()): QAPP v3, the rule this project operates under, and the ADEC 2026 QAPP guidance. Under QAPP v3, RPD is used only when one or both results are above the LOQ and one or both are at least 2x the LOQ; otherwise the pair is Not evaluable. ADEC 2026 differs for results below the LOQ: RPD is skipped when the other result is under 2x the LOQ, and the pair fails when the other result is at least 2x the LOQ. Non-detects arrive with value 0. RPD limits are those of QAPP v3 Tables 4 and 5: 20% for metals, 25% for nutrients, 5% for suspended solids.

Fecal coliform has no precision criterion in QAPP v3 Table 5 (only sterility and temperature checks), so its pairs are shown with the RPD and the status No criterion, and they never reject results. This is a project decision; a criterion should be written into the next QAPP (topics/qapp_revision_notes.md).

A pair that fails under QAPP v3 rejects both the original and the duplicate result in the export (reason Field duplicate RPD fail (QAPP v3)). The exception is a failing pair in which one result is below the LOQ (for example a detect against a non-detect). Those pairs need a decision recorded in year_files/{year}_data_flag_decisions.csv (flag Y rejects both results, N accepts, with notes); the pipeline stops before the export until each has one, and they are rejected only on Y.

20.) Were there any laboratory discrepancies, errors, data qualifiers, or QC failures (review laboratory duplicates, matrix spikes and blanks)?

The laboratory QC records (lab_qc: blanks, laboratory control and fortified samples, matrix spikes and duplicates, calibration checks, surrogates) are assessed by assess_lab_qc() against the limits the laboratory reports with each record; nothing is hardcoded. A record is Fail if any applicable check fails, Pass if at least one check passes and none fail, and Not evaluable otherwise (including a missing limit). Low-level QC (LLQC) records carry no recovery limits from SGS, so they are Not evaluable here.

Blanks are assessed under two rules side by side: the QAPP v3 rule (primary; any detection above the detection limit fails) and the ADEC 2026 rule (fails at or above the LOQ). Only the QAPP rule sets the record’s result.

A failed record rejects results through assign_qc_status(), by scope:

  • Batch controls (LCS, LCSD, CCV, ICV and similar): every result in the same batch with the same laboratory, method, analyte and fraction.
  • Blanks: detected results in the same batch, method, analyte and fraction that are below blank_multiple times the blank result. The multiple is a project convention set in config.yml; the QAPP does not state one.
  • Matrix spikes and duplicates: the parent sample only.

The Rejected results themselves are reported under Q21.

**18.) Are dissolved metal quantities less than total metals quantities?**

For every characteristic measured in both fractions at the same location and date (primary samples only), the dissolved result is compared with the total result. A Dissolved result comes from a filtered sample and a total result from an unfiltered one (SGS flags these `L` and `.` in its data deliverable; `Total` and `Unfiltered` are both treated as total). **19.) Are the duplicate sample(s) RPD (Relative Percent Difference) within range described in QAPP?**

Each original and field duplicate pair is evaluated under two rules side by side (`assess_rpd()`): QAPP v3, the rule this project operates under, and the ADEC 2026 QAPP guidance. Under QAPP v3, RPD is used only when one or both results are above the LOQ and one or both are at least 2x the LOQ; otherwise the pair is Not evaluable. ADEC 2026 differs for results below the LOQ: RPD is skipped when the other result is under 2x the LOQ, and the pair fails when the other result is at least 2x the LOQ. Non-detects arrive with value 0. RPD limits are those of QAPP v3 Tables 4 and 5: 20% for metals, 25% for nutrients, 5% for suspended solids.

Fecal coliform has no precision criterion in QAPP v3 Table 5 (only sterility and temperature checks), so its pairs are shown with the RPD and the status No criterion, and they never reject results. This is a project decision; a criterion should be written into the next QAPP (`topics/qapp_revision_notes.md`).

A pair that fails under QAPP v3 rejects both the original and the duplicate result in the export (reason `Field duplicate RPD fail (QAPP v3)`). The exception is a failing pair in which one result is below the LOQ (for example a detect against a non-detect). Those pairs need a decision recorded in `year_files/{year}_data_flag_decisions.csv` (`flag` Y rejects both results, N accepts, with `notes`); the pipeline stops before the export until each has one, and they are rejected only on Y.

**25.) Does project meet Completeness Measure A criteria?**

Measure A = Accepted results / results collected, for primary results only. The QAPP wording of this ratio is inverted; this definition is our interpolation (see `topics/qapp_revision_notes.md`). Goals are set in `config.yml` (QAPP and ADEC range).

Primary results are results from the routine environmental samples at each site and sampling event. They exclude field duplicates, field blanks and trip blanks (field QC samples), and lab-internal QC (method blanks, laboratory control samples, matrix spikes), which is kept in a separate table and never enters this measure. **28.) Are the correct monitoring locations associated with the project? Are latitude and longitude filled out in a consistent format?**

Project policy: all results are submitted under the monitoring locations already registered in CDX (the sites in the approved QAPP). New locations are not created, because that would require a modified and re-approved QAPP. When the place actually sampled differs slightly from a registered location, the difference is described in a note and the registered location is still used.

`reference/baseline_sites.csv` is the single source of site coordinates for the whole pipeline: the locations and coordinates registered in CDX. The ingest contract check, the Activity Latitude and Longitude in the export, and this section all read it (its identifiers carry the `KENAI_WQX-` prefix, removed here to match the upload IDs; the contract check and `format_wqx.R` stop if a location is not in that file).

Places the crews actually sample that differ from a registered location are recorded by the user in `year_files/sampled_locations.csv` (columns `monitoring_location_id`, `sampled_latitude`, `sampled_longitude`, `notes`; a header-only file means no differences). Nothing in the pipeline can detect a changed sampling location, so fill this file in each year from field records. Entries that differ from the registered coordinates by more than the tolerance below are listed for your attention, because the QAPP coordinates no longer describe where samples are collected. Assumption: `baseline_sites.csv` holds the coordinates registered in CDX; it was last checked against the Water Quality Portal listing of the organization's locations on `r config$sites$verified_date` (set in `config.yml`; update it when you re-check) and should be re-checked whenever sites change. Every ID in `sampled_locations.csv` must exist in `baseline_sites.csv` (the render stops otherwise); IDs with no results this year raise a warning.

Format consistency: every coordinate in the export is taken from `baseline_sites.csv`, so all locations share one source and format. The checks below therefore test that each value is numeric, that longitude is negative, and that it matches the registered value, rather than comparing the number of decimal places.

```{r q28-check}
# Differences below this distance are treated as rounding
tolerance_m <- 10

haversine_m <- function(lat1, lon1, lat2, lon2) {
  rad <- pi / 180
  a <- sin((lat2 - lat1) * rad / 2)^2 +
    cos(lat1 * rad) * cos(lat2 * rad) * sin((lon2 - lon1) * rad / 2)^2
  round(2 * 6371000 * asin(sqrt(a)), 1)
}

ref_sites <- read_csv(here("reference/baseline_sites.csv"), show_col_types = FALSE) |>
  transmute(
    monitoring_location_id = str_remove(MonitoringLocationIdentifier, "^KENAI_WQX-"),
    ref_lat = latitude, ref_lon = longitude, river_mile
  )

sampled_sites <- if (file.exists(sampled_path)) {

           col_types = cols(monitoring_location_id = col_character(),

} else {

         sampled_note = character())

    lat = suppressWarnings(as.numeric(activity_latitude)),

    numeric_ok     = !is.na(lat) & !is.na(lon),

sampled_no_results <- setdiff(sampled_sites$monitoring_location_id, site_check$monitoring_location_id)

    wrong_longitude_sign               = sum(!sign_ok),
    export_differs_from_registered     = sum(in_reference & !export_matches),
```

**32.) Are the time zones consistent and correct (AKDT in summer)?**

All sampling is in the Kenai watershed, so the correct zone follows from the date alone: AKDT from the second Sunday of March to the first Sunday of November, AKST otherwise (`akt_zone()` in `functions/clock_utils.R`, from the time zone database). The results file has no time zone columns. The WQX Web import configuration adds Activity Start and Analysis Start Time Zone as a constant (`cdx: import_config_time_zone` in `config.yml`, `AKDT` in the saved import configuration), so this check confirms that every activity and analysis date falls in that zone. If any date is AKST, the import configuration must be changed before upload.

```{r q32}
zone_tbl <- bind_rows(
  tibble(date_type = "Activity start", date = as.Date(export_dat$activity_start_date)),
  tibble(date_type = "Analysis start", date = ymd(export_dat$analysis_start_date))
) |>
  filter(!is.na(date)) |>
  distinct() |>
  mutate(expected_zone = akt_zone(date),
         import_config_zone = config$cdx$import_config_time_zone,
         consistent = expected_zone == import_config_zone) |>
  arrange(date_type, date)
zone_tbl

# Zone labels cannot show that the recorded clock times are local (a logger set to UTC would
# shift times by 8-9 hours), so activity start times are checked against a daytime window.
window_start_h <- 5
window_end_h <- 22

time_window <- export_dat |>
  mutate(start_hour = suppressWarnings(lubridate::hour(lubridate::hms(as.character(activity_start_time))))) |>
  filter(!is.na(start_hour)) |>
  summarise(n_with_time = n(),
            earliest_hour = min(start_hour), latest_hour = max(start_hour),
            n_outside_window = sum(start_hour < window_start_h | start_hour >= window_end_h),
            .by = activity_start_date) |>
  arrange(activity_start_date)
time_window
```
